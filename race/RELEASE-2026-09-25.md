# Release 2026-09-25

This release ships landing-score-v2, site-3d-resilience and start-flow, together with everything on
`main` that is not live yet (tiles-warm, ramp-single-owner). After this release:

- `SERVER_VERSION` is **1.7.1**.
- `SITE_VERSION` is **hq-1.1.1**.
- `PROTO` stays **9**.
- `CONFIG.VERSION` stays **1.7.0** until [section 4](#4-bump-configversion-and-tag-only-after-the-checklist-passes).

Live right now, checked 2026-09-25 from the office network:

```json
GET /version  {"sha":"eaac6271d6fcb000a94a7defe0062a05286787e1","version":"1.6.2","proto":9,"started_at":"2026-09-25T16:05:52Z"}
GET /health   {"ok":true,"courses":69,"tiles":{"proxy":true,"cache_writable":true,"imagery":"esri"}}
GET /tiles/terrain/0/0/0.png  200 image/png
```

So tiles-p0 (eaac627) *is* live now. CI had it green at 01:04:58Z, but the container only started
at 16:05:52Z, about 15 hours later. Before you push `deploy` again, find out why it waited that
long ([section 2](#2-unraid-diagnosis-do-this-before-pushing-main-and-deploy)). If autodeploy is
still broken, this release will sit and wait the same way.

## 1. Push commands (VS Code terminal)

First push the three feature branches and the release branch. Nothing deploys from these:

```bash
git fetch origin
git push -u origin landing-score-v2
git push -u origin site-3d-resilience
git push -u origin start-flow
git push -u origin release/2026-09-25
```

If you want PRs to review first, open them now:

```bash
gh pr create --base main --head release/2026-09-25 --title "Release 2026-09-25"
```

**`main` and `deploy` go last**, after section 2 has told you autodeploy is healthy (or you have
paused it for a manual run). Pushing `deploy` is what ships to production. Pushing `main` first
lets CI post check-runs for the SHA, and autodeploy reads those check-runs before it deploys
anything:

```bash
git checkout main
git merge --ff-only release/2026-09-25    # local main is already at 9d7e278 (landing-score-v2)
git push origin main
# Wait until all 6 checks are green for this SHA (Actions tab, or: gh run watch)
git push origin main:deploy
```

If `git push origin main` is rejected because someone else pushed first: run
`git pull --ff-only origin main`. If that fails too, stop and merge by hand. Never force-push.

## 2. Unraid diagnosis (do this before pushing main and deploy)

Run everything below as root on the Unraid box. Set these once per shell:

```bash
DATA=/mnt/user/appdata/stack/race/data
APP=/mnt/user/appdata/stack/race/app
```

**Step 0: read the evidence.** This tells you which suspect below to open:

```bash
tail -n 60 $DATA/deploy.log
cat $DATA/.deployed_sha; git -C $APP rev-parse HEAD origin/deploy
git -C $APP status -sb | head -3
docker ps -a --filter name=race --format '{{.Names}}  {{.Image}}  {{.Status}}  created {{.CreatedAt}}'
docker inspect race --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -E '^RACE_(GIT_SHA|DB)='
docker image ls race
```

| What deploy.log shows after ~01:05Z on 2026-09-25 | Suspect |
|---|---|
| Nothing at all until 16:05Z (or nothing ever for `eaac627`) | 1 |
| `FAIL eaac627… redeploy-error-pre-swap` repeating every 5 min, and the `race` container's created time does **not** change | 2 |
| `ROLLBACK eaac627… to prev ok` | 3 |
| `FAIL eaac627… redeploy-error-pre-swap` repeating, and the container's created time **does** change every 5 min | 4 |
| `SKIP eaac627… ci=none` or `ci=pending` | 5 |
| `DEPLOY eaac627… ok` at about 16:05Z | Autodeploy recovered by itself. Still check suspect 1 for the silent window before that |

The suspects are ranked by likelihood. The top one fits the evidence best: the container started at
16:05Z, which is 09:05 PDT, in working hours. That looks like someone ran it by hand.

### Suspect 1: autodeploy never ran, or exited silently (most likely)

These exits write **nothing** to deploy.log, which is why the gap goes unnoticed:

- a leftover pause file, from the hands-on work during the 2026-09-24 tile incident;
- the User Scripts schedule is gone (the RUNBOOK says the plugin "has gone missing before");
- a stale lock whose PID now belongs to some other process;
- `git fetch` failing under `set -e`.

```bash
ls -la $DATA/.autodeploy_paused $DATA/.autodeploy.lock 2>&1
[ -f $DATA/.autodeploy.lock/pid ] && ps -p "$(cat $DATA/.autodeploy.lock/pid)" -o pid,etime,cmd
cat /boot/config/plugins/user.scripts/scripts/race-autodeploy/script
grep -A3 race-autodeploy /boot/config/plugins/user.scripts/schedule.json
tail -n 30 /tmp/user.scripts/tmpScripts/race-autodeploy/log.txt 2>/dev/null
git -C $APP fetch origin deploy; echo "fetch rc=$?"
```

Any one of these outputs means this is the cause:

- `.autodeploy_paused` exists;
- the lock's PID is alive but its `cmd` isn't `autodeploy.sh`;
- there's no `race-autodeploy` script, or its schedule isn't `*/5 * * * *`;
- `fetch rc` isn't 0.

**Fix** (only the line that matches what you found):

```bash
rm -f $DATA/.autodeploy_paused                 # pause file
rm -rf $DATA/.autodeploy.lock                  # stale lock (only when no autodeploy.sh is running)
# Schedule missing: Settings -> User Scripts -> race-autodeploy -> Custom "*/5 * * * *", with the one line
#   /mnt/user/appdata/stack/race/app/race/server/autodeploy.sh
# fetch failing: fix the network or remote, then rerun the fetch until rc=0
```

### Suspect 2: redeploy.sh failed before the swap (the empty-DB guard, git, or the build)

This is the one that fits "data dir not owned by 99:100". Step 2a (the empty-DB guard) runs
**before** step 2b's `chown -R 99:100`. It opens race.db read-only *as 99:100*. If the data dir or
race.db became root-owned (for example, from a root-run container during the 09-24 incident), that
open fails. The guard then reports `missing`. Because `.deployed_sha` exists, it aborts every
tick, and it never reaches the chown that would have fixed the ownership. The old container keeps
serving 1e96f91. The same thing happens if the `python:3.12-slim` image can't be pulled, because
the check's `|| echo missing` hides that failure too.

```bash
ls -ldn $DATA $DATA/tiles $DATA/race.db $DATA/race.db-wal $DATA/race.db-shm 2>&1   # want owner 99, group 100
docker image inspect python:3.12-slim >/dev/null && echo py-image-ok
docker run --rm --user 99:100 -v $DATA:/data:ro python:3.12-slim python -c "import sqlite3; c=sqlite3.connect('file:/data/race.db?mode=ro', uri=True); print(c.execute('SELECT COUNT(*) FROM runs').fetchone()[0])"
git -C $APP checkout deploy && git -C $APP pull; echo "pull rc=$?"
docker build -f $APP/race/server/Dockerfile -t race:probe $APP; echo "build rc=$?"
```

**This is the cause** if any of these is true:

- anything in the `ls` isn't `99 100`;
- `py-image-ok` is missing;
- the sqlite line throws while race.db exists;
- `pull rc` or `build rc` isn't 0.

**Fix:**

```bash
chown -R 99:100 $DATA && chmod -R u+rwX $DATA       # ownership, including data/tiles
docker pull python:3.12-slim                         # image missing
git -C $APP branch --set-upstream-to=origin/deploy deploy   # "no tracking information" on pull
docker image rm race:probe                           # clean up the probe build afterwards
```

### Suspect 3: the new container came up unhealthy, and autodeploy rolled back

`/health` gets polled via the **public** URL, which means hairpinning from Unraid back through Caddy.
autodeploy rolls back to `race:prev` (1e96f91) when `/health` isn't a 200 with `courses > 0`
within 30 s. It can be the new container crashing on boot, or the box being unable to reach its
own hostname. `redeploy.sh` hard-codes `HEALTH_URL`, so `RACE_HEALTH_URL` can't route around a
hairpin problem.

```bash
curl -sS -m 5 -w '\n%{http_code}\n' https://race.finsonly.net/health
docker run --rm -d --name race-probe --user 99:100 -v $DATA:/app/data -e RACE_DB=/app/data/race.db race
sleep 15; docker logs race-probe 2>&1 | tail -30; docker rm -f race-probe
```

**This is the cause** if the curl prints `000` or anything other than 200 from Unraid itself. It is
also the cause if `race-probe` logs a traceback, or anything other than `Uvicorn running`.

**Fix:** for a hairpin failure, add a hosts entry on Unraid pointing race.finsonly.net at Caddy's LAN
IP (`echo "<caddy-lan-ip> race.finsonly.net" >> /etc/hosts`, then re-run the curl), or fix
NAT loopback on the router. For a crash, fix the traceback before anything else.

### Suspect 4: the tile gate (tiles.cache_writable, /tiles/terrain) failed

This gate is **new in tiles-p0**. On its own, it can't explain `/version` staying at 1e96f91. When the
gate fails, `/health` is still 200 with courses > 0, so autodeploy logs
`FAIL … redeploy-error-pre-swap` and leaves the **new** container serving. There's no rollback, and
`/version` would read eaac627. What it *does* cause is churn: `.deployed_sha` is never written, so
every 5-minute tick rebuilds and swaps again (a short outage each time). Each tick also re-tags the
failing image as `race:prev`, which wipes out the good rollback target. The release deploy passes
through this same gate.

```bash
curl -sS https://race.finsonly.net/health                                  # cache_writable must be true
curl -sS -o /dev/null -D - https://race.finsonly.net/tiles/terrain/0/0/0.png | head -5   # 200 + image/png
docker exec race sh -c 'id; ls -ldn /app/data /app/data/tiles; touch /app/data/tiles/.w && rm /app/data/tiles/.w && echo tiles-writable'
docker logs race 2>&1 | grep -i "tile cache dir"
# upstream reachability from INSIDE the container, on a tile the startup warm won't have cached:
docker exec race python -c "import urllib.request as u; print(u.urlopen('https://s3.amazonaws.com/elevation-tiles-prod/terrarium/6/10/22.png', timeout=5).status)"
```

**This is the cause** if any of these is true:

- `cache_writable:false`, or `tiles-writable` doesn't print;
- a `tile cache dir … not writable` log line appears;
- the terrain curl is 502/000, or the in-container S3 fetch times out or errors.

**Fix:** for ownership, use the `chown -R 99:100 $DATA` from suspect 2, then `docker restart race`.
Restart only with your go-ahead; CLAUDE.md requires it. If S3 is unreachable from the `proxy`
network, check DNS and egress:

```bash
docker exec race python -c "import socket; print(socket.gethostbyname('s3.amazonaws.com'))"
```

Then check the router or firewall. A temporary `RACE_TILE_PROXY=0` needs a code change,
because redeploy.sh doesn't pass extra env through.

### Suspect 5: the CI check skipped it (least likely)

CI was green on eaac627, all 6 checks by 01:04:58Z. So this only fits if the unauthenticated GitHub
API call failed from Unraid, for example because of the 60-requests-per-hour limit on a shared IP.

```bash
curl -sS "https://api.github.com/repos/eburgard7-cloud/geofs/commits/$(git -C $APP rev-parse origin/deploy)/check-runs" | grep -E '"total_count"|"conclusion"'
curl -sS https://api.github.com/rate_limit | grep -A4 '"core"'
```

**This is the cause** if deploy.log has `SKIP … ci=none` lines, the first curl fails or shows
`total_count: 0`, or `remaining` is 0. **Fix:** it clears itself at the next rate-limit reset. If
it keeps coming back, find what else on the network is using up the quota.

### Then: dry run, and deploy by hand

When the matching fix is in, run the dry run:

```bash
$APP/race/server/autodeploy.sh --dry-run
```

It should fetch, report CI passed, print the redeploy.sh commands, and stop.

Now go back to section 1 and push `main`, wait for CI, then push `main:deploy`. Then do the
deploy by hand so you can watch every step:

```bash
touch $DATA/.autodeploy_paused
git -C $APP fetch origin deploy && git -C $APP checkout deploy
git -C $APP status -sb                   # "## deploy...origin/deploy", clean
$APP/race/server/redeploy.sh --dry-run
$APP/race/server/redeploy.sh && git -C $APP rev-parse HEAD > $DATA/.deployed_sha   # only on PASS
rm -f $DATA/.autodeploy_paused
tail -n 5 $DATA/deploy.log
```

Writing `.deployed_sha` after the PASS is what autodeploy itself does on success. Without it,
the next tick would rebuild and swap the same SHA again.

**Confirm.** From the VS Code terminal on Windows, schannel needs `--ssl-no-revoke`:

```bash
git rev-parse origin/deploy
curl.exe -s --ssl-no-revoke https://race.finsonly.net/version    # sha == the line above, "version":"1.7.1"
curl.exe -s --ssl-no-revoke https://race.finsonly.net/health     # "cache_writable":true
curl.exe -s --ssl-no-revoke https://race.finsonly.net/js/config.js | findstr SITE_VERSION   # hq-1.1.1
```

## Found while preparing this release (not fixed here, out of scope)

- `redeploy.sh` runs its empty-DB guard (2a) before the chown (2b). A root-owned data dir aborts
  with a misleading "race.db is missing" and never reaches the chown that would fix it.
- `autodeploy.sh` treats a tile-gate FAIL as `redeploy-error-pre-swap`, because `/health` is still
  200. It leaves the new container running and retries every tick. Each retry re-tags that image as
  `race:prev`, so the known-good rollback target is lost.
- `redeploy.sh` hard-codes `HEALTH_URL`, but `autodeploy.sh` honours `RACE_HEALTH_URL`. A hairpin
  workaround via env only half-works.
- tiles-warm and ramp-single-owner both claimed `SERVER_VERSION` 1.6.3. This release sets 1.7.1.
